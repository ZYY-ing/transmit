# 14 节点 Ascend-Bench 部署问题复盘（下载 / 安装 / 连通）

## 0. 环境事实

| 项 | 值 |
|---|---|

| Bench Web | Runner `127.0.0.1:18787`，登录口令 `runner-token` |
| 推理入口 | `127.0.0.1:8000`（P/D 负载均衡代理，非原生 vLLM） |
| 后端 | prefill `172.27.25.14:18010`，decode `172.27.26.22:18020` |
| 企业代理 | `http://141.2.239.180:3128`（NetentSec，做 HTTPS 中间人） |
| DNS | 宿主 `141.61.33.201`；容器只有 `8.8.8.8` / `114.114.114.114` |

---

## 1. 下载阶段

### 1.1 pip 依赖下载：SSL 证书校验失败

**现象**
```
SSLError(SSLCertVerificationError(1, '[SSL: CERTIFICATE_VERIFY_FAILED]
self-signed certificate in certificate chain'))
Could not fetch URL https://mirrors.aliyun.com/pypi/simple/nltk/ - skipping
```

**根因**：出口代理对 HTTPS 做中间人解密，注入自签名 CA；同时该机器直连外网超时，只能走代理。

**修复思路**（三选一，按优先级）
1. 改用内网 HTTP 源 `http://mirrors.tools.huawei.com/pypi/simple`（不经代理、无 TLS）；
2. 必须走公网源时加 `--trusted-host <host>` 跳过该域名证书校验；
3. curl 下载场景用 `-k`，并显式 `-x http://141.2.239.180:3128`（先 `unset` 环境变量避免打架）。

### 1.2 容器内无法解析内网源域名

**现象**
```
[Errno -3] Temporary failure in name resolution  (mirrors.tools.huawei.com)
```

**根因**：容器 `/etc/resolv.conf` 被写成公共 DNS `8.8.8.8` / `114.114.114.114`，内网域名只能由公司 DNS `141.61.33.201` 解析；宿主机能解析，容器不能。

**修复**：把宿主机解析出的 IP 写入容器 hosts（临时、有效）
```bash
IP=$(getent hosts mirrors.tools.huawei.com | awk '{print $1}')   # 141.61.33.201
docker exec -u root <容器> sh -c "grep -q mirrors.tools.huawei.com /etc/hosts || echo '$IP mirrors.tools.huawei.com' >> /etc/hosts"
```

**长期方案**：`docker run --add-host mirrors.tools.huawei.com:141.61.33.201`，或给容器配 DNS `141.61.33.201`。

## 2. 安装阶段

### 2.1 setup.sh 硬编码公网源

**根因**：脚本通过 `PIP_CONFIG_FILE` 指向 `$TARGET/pip.conf`，其中写死 `https://mirrors.aliyun.com`，覆盖了宿主已配的内网源。

**修复**：改写 `$TARGET/pip.conf`
```ini
[global]
index-url = http://mirrors.tools.huawei.com/pypi/simple
trusted-host = mirrors.tools.huawei.com
progress-bar = on
timeout = 60
retries = 5
```

### 2.2 `nltk==3.8` 装不上（最隐蔽的一个）

**现象**
```
ERROR: Could not find a version that satisfies the requirement nltk==3.8 (from versions: none)
subprocess.CalledProcessError: '.../bench-venv/bin/python -m pip wheel --no-deps nltk==3.8'
```

**根因**：`benchmark/setup.py` 的 `setup_requires=['nltk==3.8']` 由 setuptools 另起一个 pip 子进程安装。**该子进程不继承外层命令行的 `-i` / `--trusted-host`，只读 pip.conf**，因此仍走阿里云 → SSL 失败 → 视为“无可用版本”。

**修复**：双管齐下
1. 先把 `nltk==3.8` 装进 venv，让 `setup_requires` 直接命中已满足；
2. 同时把 `pip.conf` 改成内网源，保证后续依赖也走内网。

### 2.3 venv 依赖冲突告警（无害）

**现象**：`pip` 报 `vllm 0.30.0+empty requires fastapi[standard]<0.137.0 ... but you have fastapi 0.123.10`

**根因**：venv 用 `--system-site-packages` 创建，能看到系统 site-packages 里的 vllm；pip 的冲突检查把系统包也算进去了。

**结论**：pip 明确打印 `Not uninstalling ... outside environment`，改动只落在 venv 内，**系统 Python 与正在运行的推理服务未受影响**，可忽略。

## 3. 启动与连通阶段

### 3.1 start-runner.sh 无法启动（路径与解释器都错）

**根因**
```bash
BASE="${ASCEND_BENCH_HOME:-/home/z00949185/ascend-test}"   # 目录不存在
exec python3 scripts/runner.py                            # 系统 python，非 venv
```
`set -euo pipefail` 下 `cd` 失败即退出，既无日志也无进程。

**修复**：重写脚本，`BASE` 默认指向 `$TARGET`，解释器改为 `$BASE/bench-venv/bin/python`。

### 3.2 重复启动导致 Address already in use

**现象**：日志里 `OSError: [Errno 98] Address already in use`，但服务其实在跑。

**根因**：`start-runner.sh` 连执行两次，第二个实例绑定 18787 失败退出。

**结论**：不影响已运行实例；启动前先 `pgrep -af '[r]unner.py'`。

### 3.3 网页连接报 504 / HIS Proxy Notification

**现象**
```
models=504  health=504
<title>HIS Proxy Notification</title>  (NetentSec)
```

**根因**：容器/宿主残留 `http_proxy`，而 `no_proxy` 不含 `141.61.141.14`，本机 API 请求被送去代理，代理再回连自身超时 → 504。

**修复**：重启 Runner 时清空代理并设置 `no_proxy`
```bash
docker exec -d -w $T -e http_proxy= -e https_proxy= -e HTTP_PROXY= -e HTTPS_PROXY= \
  -e no_proxy=127.0.0.1,localhost,141.61.141.14 <容器> bash $T/scripts/start-runner.sh
```
同时网页里服务地址改填 `127.0.0.1:8000`。

### 3.4 网页连接报 404（最终拦路问题）

**根因**：`runner.py:probe_service()` 第一步 GET `/health`；而 8000 是 `examples/disaggregated_prefill_v1/load_balance_proxy_server_example.py`，**只实现 `/v1/*`，没有 `/health`**。

实测（`--noproxy '*'`）：

| 路径 | 状态 |
|---|---|
| `/v1/models` | 200 |
| `/health` | 404 |
| `/metrics` | 404 |
| `/v1/completions`、`/v1/chat/completions`（GET） | 405（路由存在，仅 POST） |

**修复**：`probe_service` 只容忍 **404**，其余异常照常抛
```python
try:
    with opener.open(root + '/health', timeout=5) as response:
        if response.status != 200:
            raise ValueError('服务健康检查未通过')
except urllib.error.HTTPError as exc:
    if exc.code != 404:
        raise ValueError(f'服务健康检查失败：HTTP {exc.code}')
```
> 不要写成 `except URLError: pass`，那会把连接拒绝、超时、500 一并吞掉，退化成静默放过。

**补充认知**：`/health` 缺失**不是 PD 分离的固有属性**，而是该 example 代理的功能裁剪。原生 `vllm serve`、Envoy/llm-d 网关、Dynamo frontend 都有健康端点。根治办法是给入口补 `/health` 或前置网关，但那要动推理服务侧代码。

## 4. 遗留风险

| 风险 | 影响 | 建议 |
|---|---|---|
| `/etc/hosts` 手工写入 | 容器重建后失效，pip 再次解析失败 | `--add-host` 或容器 DNS 指向 `141.61.33.201` |
| 健康判定被弱化 | 后端全挂但代理存活时仍显示“已连接” | 入口补 `/health` 聚合，或 bench 侧增加 `/v1/models` 之外的后端探测 |
| setup.sh 若再次运行 | 可能把 `pip.conf` 覆写回公网源 | 运行前先 `grep -n 'aliyun\|index-url' setup.sh` |
| `start-runner.sh` 为临时重写版 | 与 kit 原始版本不一致 | 记录变更，后续升级 kit 时同步 |

## 5. 验收命令清单

```bash
# 依赖是否就绪
docker exec <容器> $T/bench-venv/bin/python -m pip show nltk ais_bench_benchmark | grep -E 'Name|Version'

# 推理 API（绕过代理）
docker exec <容器> bash -c "curl -s --noproxy '*' -o /dev/null -w 'api=%{http_code}\n' http://127.0.0.1:8000/v1/models"

# Bench Runner
docker exec <容器> bash -c "pgrep -af '[r]unner.py'; curl -s -o /dev/null -w 'runner=%{http_code}\n' http://127.0.0.1:18787/"

# 后端健康（验证 404 只发生在入口层）
for h in 172.27.25.14:18010 172.27.26.22:18020; do
  printf '%-22s ' $h; curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' --max-time 3 http://$h/health
done
```

期望：`nltk 3.8`、`ais_bench_benchmark 3.1.0`、`api=200`、`runner=200`。
